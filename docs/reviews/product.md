# 產品評審：DSH Git 面板

> 範圍：右側欄 Source Control 的完整旅程（初始化→改動→提交→同步→歷史→差異→PR→worktree）。只評產品取捨與功能邊界，不評視覺細節。最近完成的 hover 卡、分支選單、並排配色、未追蹤檔 diff、歷史軌道不在此列。

## 結論

面板把「順利的日常」做得完整：看變更、暫存、提交、推送、開 PR、切工作樹，都能在 360px 內完成，不必離開對話。真正的缺口集中在兩處：**出事後沒有下一步**（分歧、衝突、失敗訊息），以及**做完後沒有收尾**（undo commit、刪掉工作樹留下的分支）。過度設計則集中在 GitHub 的「瀏覽型」資訊與重複的刷新入口。

## 一、旅程斷點

| 站 | 現在順嗎 | 斷點 |
| --- | --- | --- |
| 初始化 | 順 | `git init` 後沒有設定 remote 的入口；只影響全新本機 repo。 |
| 日常改動 | 順 | 不能只暫存檔案中的幾行；大型 agent diff 只能整檔進出。 |
| 提交 | 順 | 成功後只能 amend，不能「復原這次提交」；誤按要開終端。 |
| 同步 | 一半 | 快進 pull 很順；本地與遠端分歧時只有一行錯誤，沒有 rebase／merge 的下一步。 |
| 衝突 | 斷 | 衝突檔只能看 diff，**沒有任何按鈕可以標記已解決**；也沒有 abort／continue。 |
| 歷史 | 一半 | 看得到軌道與 hover，但點提交沒有反應；「顯示全部」其實只到 40 筆。 |
| 差異 | 順 | 統一／並排、全文／僅變更、前後檔都完整；缺 hunk 級暫存。 |
| PR | 一半 | 建立與列表可用；看不到「目前分支那個 PR」的 checks／review 狀態。 |
| 工作樹 | 順 | 建立／切換／開啟都順；移除後分支留在原地，面板不能刪分支。 |

## 二、產品缺口

### G1 分歧後 Pull 只會失敗（P0，小）
- 場景：Agent 把 commit 推到遠端，你也在本機提交了；按 Pull 想同步。
- 斷點：`pull --ff-only` 印出 `Not possible to fast-forward`，面板只留一行錯誤，沒有 rebase／merge 選項，也不說明現在是「已分歧」。
- 建議：當 ahead>0 且 behind>0，分支列把 Pull 標成「已分歧」並提供明確的「Pull（rebase）」次要動作；錯誤訊息可展開完整 stderr、可複製。
- 少做：使用者不必自己判斷要 `git pull --rebase` 還是先 fetch，少開一次終端。

### G2 衝突檔不能標記解決（P0，小）
- 場景：pull／merge 後出現衝突，你在編輯器改完檔案回到面板，準備把衝突收掉。
- 斷點：衝突列不渲染任何列內動作；即使內容已修好，也只能到終端 `git add`。
- 建議：衝突列提供「標記為已解決」（等同 `git add`），保留「仍衝突」直到下一次 status 刷新。這不是衝突解決器，只是把最後一步留在面板。
- 少做：使用者少切一次終端；也少一次「我到底解決了沒」的來回確認。

### G3 進行中的 merge／rebase 沒有狀態與中止（P1，中）
- 場景：Agent 的 rebase 卡在中途，或 pull 留下 `MERGE_HEAD`；面板只列衝突檔。
- 斷點：看不出目前正在 merge／rebase／cherry-pick，也沒有「繼續」「中止」；使用者只能猜。
- 建議：衝突組上方出現一列狀態「正在 rebase（3 檔衝突）」＋「繼續」「中止」；只在偵測到 sentinel（MERGE_HEAD、rebase-merge 等）時出現。
- 少做：使用者不必開終端確認狀態，也不必記 `git rebase --abort`。

### G4 提交後沒有 undo（P1，小）
- 場景：在 agent 的大量變更中誤按提交，或不想讓這個 commit 存在（amend 只能改訊息）。
- 斷點：notice 只說 committed；要退回只能開終端 `git reset --soft HEAD~1`。
- 建議：提交成功的 notice 加一次性「復原這次提交（保留變更）」；只對最新且未推送的提交顯示，history 首列也可提供。
- 少做：使用者少開一次終端，也少一次「剛剛那個 commit 還在不在」的焦慮。

### G5 工作樹移除後分支仍在（P1，小）
- 場景：每個 agent 委派都留下一個 `worktree-<name>` 分支；工作樹移除了，分支卻一直累積。
- 斷點：移除只刪目錄；分支選單沒有刪除，面板也沒有「已合併」判斷。
- 建議：移除確認加「同時刪除分支（僅已合併）」；分支選單對非當前分支提供刪除，未合併時二次確認。
- 少做：使用者不必定期回終端 `git branch -d`，分支清單不會愈來愈長。

### G6 目前分支的 PR 狀態看不到（P1，中）
- 場景：剛建立 PR，想知道 CI 過了沒、有沒有人要求修改，但不想切到瀏覽器。
- 斷點：PR 清單列出所有 open PR，卻沒有以 `head=目前分支` 對應；建立後只知道編號。
- 建議：分支列下方或 GitHub 卡頂端加一列「PR #123 · checks ✓/✗ · review pending」，以 head=branch 查詢，視窗 focus 時更新；沒有 PR 時就是「建立 PR」。
- 少做：使用者少一次 DSH↔GitHub 的分頁切換，PR 卡住時能立刻知道。

### G7 歷史只能看，不能打開一次提交（P2，中）
- 場景：想確認昨天 agent 那個 commit 到底改了什麼，或找一個可挑回的修補。
- 斷點：hover 卡有 stat 與 GitHub 連結，但點列沒有動作；本機內容只能去終端 `git show`。
- 建議：點提交在既有 diff 分頁開「這次提交的變更檔清單＋diff」（唯讀），先不做 cherry-pick／revert；同時把「顯示全部」改成「顯示最近 40 筆」。
- 少做：使用者少開一次終端，也少一次「先 push 才能在 GitHub 看」的繞路。

### G8 工作樹的 clean 與移除條件不一致（P2，小）
- 場景：某個工作樹只有未追蹤檔；列表顯示 clean，按移除卻失敗。
- 斷點：骯髒計數刻意排除 untracked，但 `worktree remove` 會因 untracked 拒絕；訊息只說失敗。
- 建議：標籤改成「0 已追蹤變更」，或在移除失敗時明講「內有未追蹤檔」並提供開啟該目錄的動作。
- 少做：使用者不必自己猜為什麼 clean 的工作樹移除不了。

### G9 骯髒工作區沒有 stash 可用（P1，中）
- 場景：改到一半，遠端有更新要 pull，或要切到 agent 的分支；但工作區是髒的。
- 斷點：pull／switch 會失敗；不想提交半成品，也不想按放棄把改動丟掉。
- 建議：提交框旁提供「暫存目前變更」與「取回最近一次暫存」，顯示 stash 數量；只做建立／取回，不做完整 stash 管理。
- 少做：使用者少一次 `git stash`／`git stash pop`，也少一次「先隨便 commit 再 undo」的壞習慣。

## 三、過度設計（低價值或干擾）

- **沒有 GitHub 遠端時永久顯示一張空卡**（P2，小）：本機 repo 每次都看到「沒有 GitHub 遠端」。`connected=false` 時整卡收起，只留頁首的 repo 資訊即可。
- **兩個刷新入口**（P2，小）：頁首刷新與「重新讀取工作區」圖示功能重疊，使用者要先想「哪個才會讀到新工作區」。合併成一個刷新，把重讀工作區收進 repo 下拉的次要動作。
- **GitHub 星標／復刻／issue 數與 Issues 分頁**（P2，中）：這是瀏覽型資訊，不是提交或同步的一步，在窄欄卻佔掉可貴高度。保留「在 GitHub 開啟」與 PR 狀態列，Issues 清單移到外開即可。
- **prune 剪刀常駐**（P2，小）：沒有 prunable 列時它永遠沒用，還增加一個誤點目標。只有列表出現 prunable 時才顯示。

## 四、最值得做的三件事

1. **讓衝突能收尾（G2＋G3，P0，小～中）**：先加「標記為已解決」，再加 merge／rebase 狀態列與「繼續／中止」。這是目前唯一「看得到卻完全做不下去」的流程斷點。
2. **同步失敗給下一步（G1，P0，小）**：分歧時提供明確的 rebase 路徑，錯誤可展開。右欄最常遇到的失敗就是這一種，修好它等於少開一半的終端。
3. **工作樹生命週期閉環（G5＋G8，P1，小）**：移除工作樹時一併處理分支，並修正 clean 的語意。這是 DSH「一次委派多個 worktree」的差異化場景，別讓它以分支垃圾收場。

## 五、明確不建議做

- **完整三方合併／衝突編輯器**：360px 放不下，DSH 編輯器本來就能開檔；面板只負責標記、繼續、中止。
- **全頁 commit graph／blame／檔案歷史**：需要整頁與搜尋，超出右欄尺度；VS Code 也是另開 editor tab。
- **在面板內讀 PR 討論、review、issue 詳情或留言**：重複 GitHub 且需要寬版；只留一行狀態與外開連結。
- **在面板內自動 merge／rebase 工作樹分支**：風險高，衝突時又回到同一個問題；先做刪分支與建立 PR。
- **多 repo 同時總覽／跨 repo dashboard**：右欄是 session 範圍，會與 DSH 的工作區概念打架。
- **更頻繁的檔案監看／即時刷新**：成本高，8 秒輪詢已足夠；這是主機能力，不是產品缺口。
- **提交時自動 push，或預設開啟全部暫存**：增加誤提交與誤推送；保留明確的兩個步驟。

## 交叉評審回應

### 1. 同意並借用

- **poweruser F1（差異頁不能暫存）**：我第一輪把「差異」判成順，只提 hunk 級暫存，低估了 review 回圈。同意把「diff header 加 `+`／`↩`」提前，這比我原本的 G7（點歷史看 diff）更常發生。
- **poweruser F2＋F3＋engineer #3／#4**：我的 G1／G2 都假設使用者看得到錯誤；但 notice 會被捲出畫面、被 8 秒輪詢清掉、busy 還會被覆蓋。這些是「下一步」的前提，借用為 G1／G2 的依賴條件。
- **poweruser F4（amend 靜默改寫訊息、stageAll 殘留）**：比我原本的 G4 undo commit 更危險——一個是事後補救，一個是事前防止資料被覆寫。接受 amend 預覽與提交後重設 stageAll。
- **gitexpert pathspec `:(literal)`**：直接命中我的 G2「標記已解決＝`git add`」；含 `[` 的檔名會誤 add 別的檔。G2 若做，路徑一律 literal。
- **gitexpert 衝突 diff `--cc` 壞掉＋衝突中可直接 commit**：我原本只說「衝突列沒有按鈕」，漏了「點開 diff 是錯的」「有衝突還能 commit」。G2 必須擴大成三件事：正確降級 diff、擋 commit、才能標記解決。
- **engineer #9／gitexpert GHES**：支持我的「沒有 GitHub 遠端就收起空卡」，並補上非 github.com origin 的 404 誤報。
- **poweruser stash 值得做**：與我的 G9 互相驗證，維持 P1。

### 2. 不同意

- **design 把 focus-visible 列 P0**：我不同意這個優先級。它是真缺陷，但不會讓日常流程中斷；本輪 product 的 P0 仍應留給「按了沒反應」與「衝突無法收尾」。
- **poweruser 把 hunk 級暫存與 F1 同列 P1**：方向同意，但 360px 的 hunk 按鈕要先有檔案級動作與穩定的 diff header；順序應是 F1 → hunk，不是同時。
- **design 的 hover 卡寬度（max-width 400→320）**：我第一輪已把 hover 卡列為近期完成、不在範圍；維持不在本輪優先，不反對後續修。
- **gitexpert 的 bare repo 判定**：正確性上同意，但 DSH 的委派流程幾乎不會用 bare repo，產品優先級低於衝突與錯誤生命週期；列 P2 即可。

### 3. 修正自己

- **「差異 順」降級為「一半」**：並排在 360px 截斷（poweruser F11）、預設全文、衝突 diff 解析錯誤（gitexpert），我原本的旅程表過度樂觀。
- **G2 升級並改寫**：不是加一顆按鈕，而是「衝突 diff 降級 → 禁止衝突中 commit → 才能標記已解決」，且 add 要走 literal pathspec。
- **G1 加強**：錯誤可展開之前，先讓錯誤 sticky、不被輪詢清掉；否則「下一步」等於沒顯示。
- **G4 降級**：先借 poweruser F4 的 amend 防護，undo commit 仍做但排在其後。
- **G5／G8 暫留 P1**：交叉評審沒有反對，但也沒有新的高頻證據；仍是我眼中 DSH 的差異化場景，但不再是 Top 3。

### 4. 最終 Top 3

1. **先修「按了沒反應」**（poweruser F2／F3／F10＋engineer #3／#4／#5／#6）：錯誤 sticky、可展開、不被輪詢清掉，busy 不再被覆蓋——所有後續改進都建立在看得見回饋上。
2. **衝突／分歧要能正確收尾**（G1＋G2＋G3＋gitexpert `--cc`／literal／擋 commit）：這是唯一完全做不下去的斷點，而且不能只補按鈕卻讓指令打錯檔。
3. **補完 review 回圈**（poweruser F1＋F4）：diff 頁直接暫存／放棄、amend 先預覽——每天幾十次的操作，勝過低頻的歷史瀏覽與 PR 細節。
